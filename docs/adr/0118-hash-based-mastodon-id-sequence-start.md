# ADR-0118: Mastodon ID のシーケンスは IRI のハッシュを起点に空きを探す

- **Status:** Accepted
- **Date:** 2026-10-12

## 背景

Issue #282。Follow 殺到の負荷試験で inbox の各ミドルウェアの所要時間を計測したところ、
遅延の大半は `verifySignature` で初見の送信者 actor を保存する `Store#saveObject` (p50 約 8 秒、最大 16 秒) だった。
JSON-LD の処理やリモートへの HTTP 取得は合わせて 0.5 秒程度にすぎない。

原因は Mastodon ID の採番である。Mastodon の actor の `published` は作成日の 0 時
(`created_at.midnight`) なので、同じ日に作られたアカウントはすべて同じタイムスタンプになる。
シーケンスを 0 から 16 件ずつ探すため、

- 同じタイムスタンプの k 件目の採番に約 k/16 回の逐次読み取りが必要になる。
- 並行するトランザクションがすべて同じ `mastodonIds` ドキュメントを読むため、ロック競合で直列化・再試行される。

引っ越し時は、同じ日 (例えば pawoo.net の開設直後) に作られたアカウントのフォロワーが集中しうる。

## 決定

- 空きシーケンスの探索を、**IRI の SHA-256 の先頭 16 bit を起点**とし、65,536 で折り返しながら行う。
  IRI を持たないメディア添付の採番は乱数を起点にする。
- レイアウト (`ミリ秒 << 16 | シーケンス`)、`published` 基準のタイムスタンプ、マッピングの保存先は [[ADR-0058]] のまま変えない。

## 理由

- Mastodon 本体もシーケンス部をテーブル名・時刻のハッシュを起点にして決めている
  (`third_party/mastodon/lib/mastodon/snowflake.rb`)。
- 起点が IRI ごとに散らばるので、同じタイムスタンプでも大半は最初の読み取りで空きが見つかり、
  並行するトランザクションの読み取り対象も重ならない。
- 同一ミリ秒内の順序はもともと採番の順序にすぎず、時系列としての意味はない。
  ID の大小がタイムスタンプ順になる性質は保たれる。

## 結果

- 既存の ID は変わらない。新規の採番だけが新しい規則に従う。
- 同一ミリ秒内の ID の並びは保存順ではなくなる。
