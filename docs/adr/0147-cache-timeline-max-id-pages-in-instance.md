# ADR-0147: ホーム・リストのタイムラインの `max_id` だけのページも、バージョンを見てインスタンス内にキャッシュする

- **Status:** Accepted (検証の読み取りの頻度は ADR-0154 で Superseded)
- **Date:** 2026-10-23
- **Supersedes:** [ADR-0139](0139-cache-timeline-head-page-in-instance.md) の対象 (決定1) と上限 (決定6)

## 背景

ADR-0139 の後も、本番の Firestore の読み取りは 1 日約 76 万回あり、見積もり (約 14 万回) の約 5.5 倍だった。
Phanpy の自動更新は先頭ページを取り直したあと、表示が短いと「Show more」が画面の近くに入るので、
同じ `max_id` で 2 ページ目も取り直す (`timeline.jsx` の `InView`)。2026-10-22 (PT) には、この 2 ページ目が
リストで 5,289 回、ホームで 1,979 回あり、どれも全体を組み立てていた (1 回あたり約 100 回の読み取り)。

## 決定

1. **対象:** 先頭ページに加えて、`max_id` だけを持つページ (`since_id`・`min_id` が無い) もキャッシュする。
   キーは閲覧者・タイムライン・`limit`・`max_id`。`since_id`・`min_id` のあるページは従来どおりキャッシュしない。
2. **検証:** `max_id` のページは、マーカー・following のバージョン・閲覧者のバージョン (ADR-0139 決定2・3) を
   `getAll` で読み (計 3 回)、組み立てたときと同じなら組み立て済みの Status の配列を返す。
   新着はどれも `max_id` より新しく、このページには入らないので、最新のエントリは読まない。
3. **TTL:** 先頭ページと同じく、組み立ててから 15 分 (ADR-0139 決定5)。
4. **上限:** 先頭ページと同じ LRU に入れ、上限を 64 件 (キー単位) に増やす。

## 理由

- ページの中身は `max_id` より古いエントリと、可視性の判定の入力だけで決まる。後者はバージョンで捉えられ、
  前者が変わるのは遅れて届いた古い ID のエントリと、リモートの削除・編集だけで、先頭ページも TTL で反映している。
- 先頭ページが変わると Phanpy の 2 ページ目の `max_id` も変わり、新しいキーで組み立て直す。
  古いキーは LRU で落ちる。上限を増やすのは、先頭ページが 2 ページ目に追い出されないようにするため。

## 結果

- 2 ページ目の取り直しは、ルートの認証などを含めて 1 回あたり約 6〜7 回の読み取りになる。
  組み立て直すのは、先頭ページが変わったときと 15 分ごとだけになる。
- メモリは最大で十数 MB 増える。`mastodonApi` の割り当て (256MiB) は変えない。
