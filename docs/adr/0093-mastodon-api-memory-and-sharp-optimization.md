# ADR-0093: mastodonApi のメモリ引き上げと画像処理最適化

- **Status:** Accepted
- **Date:** 2026-10-07

## 背景

ADR-0091 にてメディアアップロード (最大 10MB / 16MP) を実装したが、Cloud Functions v2 の既定メモリ 256 MiB では、スマートフォン写真のアップロード時に `multipart/form-data` 受信と `sharp` によるデコード・リサイズ・EXIF 除去・Blurhash 計算が重なり、メモリ使用量が 285 MiB を超過して OOM (signal 6) による 503 エラーが発生した (Tusky 実機検証)。
また Tusky 等のクライアントは複数枚の画像を同時に並行アップロードするため、単一コンテナ内で画像処理が重なると 1GiB でもメモリ不足に陥る。
メディア処理の安定稼働に必要なリソース割り当てとライブラリ設定を決定する。

## 決定

- **`mastodonApi` のメモリ割り当て:** `https.onRequest({ memory: '2GiB' }, app)` として 2GiB を割り当てる。
- **sharp キャッシュの無効化と並行度制限:** `sharp.cache(false)` および `sharp.concurrency(1)` を設定し、コンテナ内での画像バッファ保持を抑制するとともに、ホストコア数依存のワーカースレッドによるメモリプール膨張を防ぐ。

## 理由

- Tusky 等による複数画像の並行アップロードや高解像度画像の処理では、V8 ヒープと libvips の作業メモリが合算され 1GiB を超えうる。2GiB を割り当てることで 1.0 vCPU が確保され、CPU スロットリングが解消されて処理時間が大幅に短縮され、メモリ保持時間も短縮される。
- sharp (libvips) はデフォルトでホストマシンの CPU コア数ぶんのスレッドを生成し、スレッドごとにメモリを確保するためサーバーレスコンテナでメモリ断片化と枯渇を招きやすい。`sharp.concurrency(1)` によりメモリ使用量を最小化できる。
- Cloud Run / Cloud Functions の料金は使用メモリ量と実行時間に比例するが、個人インスタンスの低トラフィック下では無料枠内に収まり、運用コストへの影響は軽微である。
