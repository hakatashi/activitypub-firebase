# ADR-0167: Firestore のバックアップと PITR をプロジェクトごとに絞る

- **Status:** Accepted
- **Date:** 2026-10-27

## 背景

- 3 プロジェクトとも、日次と週次(木曜)のバックアップを、どちらも保持 98 日で撮っている。この設定はリポジトリでは管理していない。
- 本番と dev は PITR も有効になっている。bots は PITR が無効である。
- Firestore のバックアップは毎回 DB 全体を保存するので、費用は「保持する件数 × DB のサイズ」で決まる。
  - 98 日分たまると、本番と dev でそれぞれ約 112 件になり、合わせて月約 800 円かかる(10/27 の DB サイズ:本番 593 MiB、dev 632 MiB)。
  - 単価(東京):バックアップ 5.97 円/GiB月、PITR 18.77 円/GiB月。
- 本番の DB は 1 日約 28 MiB ずつ増えている。
- #420 は、3 年運用後の費用を 3 プロジェクト合計で月 500 円以内に収めることを目標にしている。

## 決定

1. **dev:** バックアップのスケジュールと既存のバックアップをすべて削除し、PITR を無効にする。
2. **bots:** バックアップのスケジュールと既存のバックアップを削除し、PITR を有効にする。PITR だけで守る。
3. **本番:** 日次のバックアップの保持期間を 7 日に短くし、7 日より古い日次バックアップを削除する。週次(保持 98 日)と PITR は今のまま残す。
4. **見直し:** DB が大きくなったら、本番のバックアップの保持期間を短くするか、バックアップをやめることを検討する(#422)。
5. 設定は今までどおり gcloud で手作業で変え、リポジトリでは管理しない。

## 理由

- **dev:** 検証のためにデータを壊してよい環境なので(AGENTS.md)、戻す手段は要らない。
- **bots:** DB は 10 MiB しかないので、PITR の費用は月 1 円にも満たない。ボットの設定や投稿を誤って壊したときに直近 7 日の任意の時点に戻せれば十分なので、バックアップは撮らない。
- **本番の日次:** 直近 7 日は PITR で 1 分単位に戻せるので、7 日を超えて日次を残す意味は小さい。7 日より古い時点には週次で戻せる。
- **本番の PITR:** 月約 11 円(DB 1 GiB あたり約 19 円)と安く、誤操作や不具合の直後に戻すときに最も役に立つ。
- **他の案:** 日次 3 日・週次 4 週にする案も検討した。ただ、DB が小さいうちは差が小さいので、今は 1 か月より古い時点に戻せることを優先した。

## 結果

- 今の DB サイズで、3 プロジェクトのバックアップと PITR の費用は月約 85 円で落ち着く。今の設定のままたまりきった場合は月約 820 円なので、約 1/10 になる。
- dev は、どの時点にも戻せなくなる。bots は、7 日より古い時点に戻せなくなる。
- 本番は、日次バックアップ 7 件と週次 14 件で、つねに DB 21 個分を保存する。
  - 今のペースで DB が増え続けると、3 年後(約 31 GiB)には、本番のバックアップ・PITR・保存で月約 4,900 円になる。
  - 単一フィールドインデックスを除外した場合(#424、3 年後に約 5.5 GiB)でも月約 860 円で、目標を超える。#422 の見直しは必須である。
- スケジュールの保持期間を変えても、既存のバックアップの `expireTime` は変わらない前提で、古いものは手で削除する。
