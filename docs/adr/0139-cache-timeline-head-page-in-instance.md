# ADR-0139: ホーム・リストのタイムラインの先頭ページを、新着とバージョンを見てインスタンス内にキャッシュする

- **Status:** Accepted (対象と上限は ADR-0147、検証の読み取りの頻度は ADR-0154 で Superseded)
- **Date:** 2026-10-21

## 背景

Issue #347。Phanpy の自動更新は、アイドル状態のカラムで先頭ページ(`limit=20`、カーソルなし)を 15 秒ごとに取り直す。
ADR-0136・ADR-0138 の後もホーム・リストは 1 回あたり約 100 回の読み取りで、その大半は毎回同じ 20 件の Status の組み立てである。

## 決定

1. **対象:** `max_id`・`since_id`・`min_id` の無い先頭ページだけ。キーは閲覧者・タイムライン(ホームかリスト ID)・`limit`。
   射影のマーカー(ADR-0136 決定5)が無いときはキャッシュしない。
2. **検証:** リクエストごとに、マーカー・following のバージョン(ADR-0135)・閲覧者のバージョン(下記)を `getAll` で読み、
   射影の最新のエントリの ID をクエリで読む(計 4 回)。3 つの `updateTime` が組み立てたときと同じで最新のエントリも同じなら、
   組み立て済みの Status の配列を返す。following のバージョンが無ければキャッシュしない。どれも組み立ての前に読む。
3. **閲覧者のバージョン:** `userInfos/{actor}/projectionVersions/timelineView`。閲覧者が Status の見え方を変える
   Mastodon API(投稿・削除・お気に入り・ブースト・ブックマーク・ピンとその取り消し、フォロー・フォロー解除、
   プロフィールの更新、リストの変更・削除・メンバーの追加・削除)を呼んだとき、**応答を返す前に**書き直す
   (ルートに付けるミドルウェアが `res.json` を待たせる)。応答の後に書くと、直後の再読み込みが古い
   `favourited: false` などを返し、Phanpy の表示が巻き戻る。無ければ読み出し時に作る。
4. **新着があったとき:** 最新のエントリが前回より新しければ、前回の最新より新しい分だけを `since_id` で組み立てて先頭に足し、
   ID で重複を除き、ブーストの重複(ADR-0096)を新しい方に寄せて `limit` 件に切る。足した結果が前回より短くなるとき
   (前のブーストが落ちたとき)と、最新のエントリが前回より古いときは全体を組み立て直す。
5. **TTL:** 全体を組み立ててから 15 分で組み立て直す(新着を足しても延ばさない)。リモートで変わるお気に入り数・
   ブースト数・返信数、リモートの投稿の編集・削除、リモートの actor の更新、遅れて届いた古い ID のエントリは、
   無効化せずこの間に反映する。
6. **上限:** 32 件(キー単位)の LRU。インスタンスごとに持ち、バージョンと射影は全インスタンスで共通なので食い違わない。

## 理由

- 可視性は組み立て時に従来どおり判定する(ADR-0136 決定3)。判定の入力のうち、フォロー関係は following のバージョン、
  リスト・`exclusive` は閲覧者のバージョンで変化を捉えるので、フォロー解除した相手の private な投稿がキャッシュから見え続けない。
- 閲覧者のバージョンは書き込みの経路ごとではなく API の入口で書き直すので、Store を通らないブックマーク・ピン・リストも漏れない。
- 先頭ページだけに絞れば、キーが数件で済み、新着の検出もエントリ 1 件のクエリで済む。

## 結果

- 新着も操作も無いポーリングは、ルートの認証などを含めてホーム約 7 回・リスト約 8 回の読み取りになる。
- 閲覧者の書き込み系の API 1 回ごとに書き込みが 1 件増える。
- リモートの削除・編集・件数は最大 15 分遅れて反映する。Mastodon API 以外(コンソール・スクリプト)で閲覧者の状態を
  変えたときも、15 分で反映する。
