# ADR-0001: 軽量 ADR で設計判断を記録する

- **Status:** Accepted
- **Date:** 2026-09-03

## 背景

このプロジェクトは今後、原則としてコーディングエージェントが実装を進める。エージェントはセッションを
またいで記憶を持たないため、引き継ぎはリポジトリにチェックインされたドキュメントに完全に依存する。

一方で、単一の大きなドキュメント(現行の `AGENTS.md` がまさにそうなりかけていた)に現状分析・設計判断・
既知の問題・進捗をすべて書き足していくと、数セッションで読み切れない長さになり、
古い記述と新しい記述の区別がつかなくなる。

## 決定

設計判断は `docs/adr/` 以下に **1決定1ファイルの軽量 ADR** として記録する。書式とルールは
[`docs/adr/README.md`](README.md) に定める。

責務を次のように分離し、それぞれの文書に他の役割の内容を書かない。

| 置き場所 | 書くもの |
|---|---|
| `AGENTS.md` | プロジェクトの概要、ドキュメントの地図、エージェントの作業ルール |
| `docs/adr/` | 設計判断とその理由(追記専用) |
| `docs/architecture.md` | **現時点の**アーキテクチャ。履歴は書かない |
| `docs/known-issues.md` | 既知の不具合・技術的負債 |
| GitHub Issue | 進捗、TODO、作業の議論 |

## 理由

ADR は追記専用なので、過去の判断が新しい判断で上書きされて消えることがない。1ファイルが小さいため、
エージェントは必要な決定だけを読める。決定が覆った場合も `Superseded by` で追跡できる。

代替案として GitHub Wiki や Issue に決定を集約する案もあったが、エージェントがリポジトリを
チェックアウトした状態でオフラインに読めないため採らなかった。

## 結果

- 新しい設計判断をする際は、実装を始める前に ADR を追加する義務が生じる。
- `AGENTS.md` には決定の理由を書かず、ADR へのリンクのみを置く。
- ドキュメントの肥大化は、ファイル数の増加として現れる(1ファイルの肥大化としては現れない)。
